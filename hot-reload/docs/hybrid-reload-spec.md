# 업무 코드 재로딩과 인프라 전체 재시작 스펙

상태: 구현 기준, 2026-09-30. 기존 `hot-reload-project-spec.md`의 초기 생성 지시서를 대체한다.

## 목표와 계약

표준 Spring Boot starter의 JAR·소스를 수정하지 않는다. 자주 변경하는 업무 코드는 부모 빈과 서버를
유지하면서 새 클래스로더·자식 컨텍스트로 교체한다. 유지 인프라에 영향을 주는 변경은 서버와 JVM을
포함한 전체 애플리케이션 재시작으로 반영한다. 부분 교체가 안전하다고 판단하지 못한 파일 변경은
전체 재시작으로 분류한다. 전체 재시작은 서비스 중단과 인메모리 상태 소실을 수반한다.

starter 무수정 사용과 임의의 starter 기능을 부분 재로딩하는 것은 서로 다른 계약이다. 부모의 자동
구성과 자원은 그대로 사용하지만, 자식 빈을 처리하는 확장 기능에는 세대별 연동이 필요하다. 지원되지
않는 기능은 유지 영역에 두거나 `business-packages`를 비워 일반 Boot + 전체 재시작 모드를 사용한다.
업무 패키지 지정은 해당 코드가 아래의 경계를 지킨다는 애플리케이션의 명시적인 선택이다.

## 실행 모드

- `reload.enabled=false`: 재로딩 엔진 비활성. 일반 Spring Boot 실행.
- enabled + `business-packages` 없음: 일반 Boot MVC·자동 구성을 유지하고 파일 변경을 전체 재시작으로 처리.
- enabled + `business-packages` 지정: 부모는 서버·인프라, 자식은 선택한 업무 코드와 세대별 실행 인프라를 소유.
- 전체 JVM 재시작은 외부 `RestartLauncher` 아래에서 실행할 때 자동화된다. 감독자가 없으면 현재
  프로세스를 종료하지 않고 `restart-required`/HTTP 409로 알린다. 임베딩 환경은 `FullRestart` 빈으로
  재시작 동작을 제공할 수 있다.

## 소유권

부모에 남기는 대상은 웹 서버, DB 연결 풀, 공용 외부 클라이언트, 변경하지 않는 ORM/매퍼 설정과 그
설정이 사용하는 엔티티·공통 타입이다. `business-packages` 밖과 `parent-packages` 안은 부모 소유다.
애플리케이션 설정 클래스와 그 중첩 클래스도 부모에 둔다.

자식은 컨트롤러, 업무 서비스, 웹 DTO, 세대별 MVC, 프록시 생성기, 메서드 메타데이터·직렬화 캐시를
가진다. 라이브러리 클래스가 부모 클래스로더에서 로드되더라도 해당 빈은 자식에 새로 만들 수 있다.
부모 코드가 자식 타입을 직접 참조하거나 부모 레지스트리·세션·캐시에 자식 객체를 영구 보관해서는
안 된다. 부모 컨텍스트는 자식 빈을 직접 조회할 수 없다.

초기 권장 범위는 웹·업무 서비스다. JPA 엔티티·리포지토리, MyBatis 매퍼, 보안·서버 설정,
스케줄러·메시지 소비자 설정은 유지 영역에 둔다. 이들의 변경은 전체 재시작한다. 사용자 정의
애너테이션/리플렉션/외부 등록에 의한 숨은 의존성은 완전하게 정적 추론하지 않는다.

## 변경 분류

감시, HTTP API, `GenerationManager.reloadWithResult()`는 하나의 `ChangePlanner`와 적용된 baseline을 쓴다.

| 변경 | 동작 |
|---|---|
| 업무 영역의 일반 클래스·DTO 추가/수정/삭제 | 자식 세대 교체 |
| 부모 소유 클래스 | 전체 재시작 |
| `@Configuration`, `@Bean`, `@Enable*`, 설정 프로퍼티, 엔티티·매퍼·리포지토리, 예약/메시지 리스너 변경 | 전체 재시작 |
| 직접 구현한 Servlet/Filter, MVC configurer, BeanPostProcessor 등 인프라 타입 변경 | 전체 재시작 |
| 리소스·설정·의존성 JAR·감시하도록 지정한 빌드 파일 변경 | 전체 재시작 |
| 읽을 수 없는 클래스 형식 | 전체 재시작 분류; 스냅샷 자체를 읽지 못하면 기존 상태 유지 + 오류 |
| 업무와 인프라가 함께 변경 | 전체 재시작 우선, 부분 적용 금지 |
| 클래스/리소스의 바이트가 동일한 재컴파일 | 감시에서는 무시 |
| 변경 없는 명시적 API 호출 | hybrid에서는 세대 재생성, 일반 모드에서는 전체 재시작 요청 |

클래스·리소스는 SHA-256으로 비교한다. 의존성 JAR는 크기/수정 시각으로 감지한다. JAR를 변경하면서
이 메타데이터까지 보존한 경우에는 수동 재시작이 필요하다. `reload.classpath`, 실행 클래스패스의
디렉터리/JAR, `reload.watch-paths`를 검사한다. 클래스패스 밖의 설정·빌드 파일은 watch-paths에 넣는다.
전체 디렉터리를 재귀 감시할 때 로그·생성물까지 포함하지 않도록 경로를 좁혀야 한다.

전체 재시작 후 새로 해석할 명령을 감독자에 제공한다. 예를 들어 Gradle `bootRun` 명령을 다시 실행하면
변경된 build.gradle과 의존성 그래프도 다시 해석된다. 고정 `java -cp` 명령은 그 클래스패스만 재사용한다.

## 부분 교체 절차

1. 현재 파일 스냅샷과 마지막 적용 baseline을 비교한다. 감시 모드는 quiet-period 동안 안정화를 기다린다.
2. 업무 변경이면 새 클래스로더와 자식 컨텍스트를 생성한다. `GenerationIntegration.configure`를 적용한다.
3. refresh, DispatcherServlet 초기화, 통합 검증을 완료한다. 생성 도중 파일이 다시 변경되면 공개하지 않는다.
4. 성공한 경우에만 현재 세대와 baseline을 교체한다. 이전 세대는 진행 요청을 drain한 뒤 종료한다.
5. 실패하면 새 세대를 폐기하고 기존 서비스와 baseline을 유지한다. 수정 후 감시 또는 API로 다시 시도한다.

삭제된 업무 클래스는 부모의 이전 클래스 사본으로 fallback하지 않는다. 동일한 스냅샷을 반복 생성해도
삭제 정보가 유지된다. 감시의 quiet-period가 빌드 완료를 보장하지는 않으므로 대규모 빌드는
컴파일 완료 후 API를 호출하는 방식을 권장한다.

## 전체 재시작 절차

`RestartLauncher -- <명령> [인자...]`가 별도 애플리케이션 프로세스를 시작하고 비공개 임시 요청 파일
경로를 환경 변수로 전달한다. 엔진은 재시작 요청을 비동기로 예약하고 API에는 202를 돌려준다. 이어
감독자에게 요청을 기록하고 컨텍스트를 닫은 뒤 JVM을 종료한다. 감독자는 명령 종료를 기다린 후 같은
명령을 다시 실행한다. 명령은 셸 문자열로 합치지 않고 인자 배열 그대로 실행한다.

202는 완료가 아니라 요청 수락이다. 새 프로세스의 readiness로 완료를 확인한다. 새 프로세스가
기동에 실패하면 새로운 요청 파일이 없으므로 감독자도 종료하여 무한 재시작하지 않는다. 이미 종료된
이전 JVM으로 자동 롤백하지 않는다. 디버거 JVM 옵션·포트는 실행 명령에서 지정한다.

## 세대별 확장

부모의 `GenerationIntegration` 빈을 순서대로 발견한다. `configure`는 자식 refresh 전에 설정을
등록하고 `validate`는 DispatcherServlet 초기화 후 공개 전에 계약을 검사한다. 구현 객체는 부모에
남으므로 자식 컨텍스트·클래스·인스턴스·예외 객체를 필드에 저장하지 않는다.

엔진의 기본 자식 기능은 MVC, 부모 ObjectMapper 설정을 복사한 JSON 변환, AspectJ 프록시,
부모 트랜잭션 매니저를 사용하는 세대별 트랜잭션 advisor, 캐시 advisor, 메서드 검증이다.
Boot의 `WebMvcRegistrations`가 제공하는 handler mapping/adapter/exception resolver는 각 세대에서
생성한다. 부모 advisor 인스턴스는 자식에 그대로 복사하지 않는다.

`GenerationManager.withGeneration`은 비 HTTP 진입점에서 세대를 acquire하고 동기 호출이 끝나면
release한다. 중첩 호출은 이미 고정된 세대를 사용한다. HTTP도 같은 `GenerationScope`를 사용한다.
스코프는 임의의 executor로 자동 전파하지 않는다. 백그라운드 작업·비동기 메시지 소비·자식 객체가
들어간 세션/공용 캐시에는 별도 생명주기 계약이 필요하다.

## ProObject 22 연동

ProObject HTTP 어댑터가 클래스패스에 있으면 hybrid에서 전용 통합을 활성화한다. starter를 수정하지
않고 부모에 등록된 실행용 @Bean 정의만 세대별 singleton으로 다시 구성한다. 대상은 클래스로더 holder,
ObjectFactory/파서 캐시, ComponentApplicationContext, dispatcher, 서비스 매니저·핸들러,
선후처리·이미지로그·trace·예외 처리·서비스 aspect다. 서버, ApplicationManager, 메타, 연결 풀은 부모에 유지한다.

부모의 ProObject dispatcher에는 세대 선택 프록시를 두고 실제 dispatch는 고정한 세대의 dispatcher로
위임한다. 자식에서는 현재 세대의 컨텍스트와 클래스로더로 컨트롤러·DTO를 찾는다. HTTP 어댑터가
ProObject 어댑터인지, 필수 실행 빈이 자식에 실제로 존재하는지 확인한 후에만 세대를 공개한다.

ProObject 22의 표준 @Bean 이름과 factory method 계약을 대상으로 한다. 사용자 정의 교체 빈,
JEUS 전체 배포·트랜잭션, 원격 호출, 비동기 이미지로그/메시지 등은 실제 소비자 환경에서 추가 검증해야 한다.
서비스 XML/메타 변경은 전체 재시작하며, 외부 디렉터리에 있으면 watch-paths로 감시한다.

## 검증 기준

- 업무 변경 시 PID·서버·부모 자원 identity 유지, 응답은 새 버전.
- 인프라 또는 혼합 변경 시 새 PID에서 새 인프라·업무 버전 적용.
- API와 감시가 같은 정책 사용. 감독자가 없으면 409이고 기존 세대 유지.
- 부분 생성 실패 시 기존 응답 유지, 전체 재시작 기동 실패는 반복하지 않음.
- 중첩 호출이 이전 세대에 고정되고 마지막 요청 종료 후 폐기.
- 삭제 클래스 fallback 금지, 반복 교체 후 이전 클래스로더 회수.
- 표준 MVC 확장과 검증 기능, 실제 ProObject 어댑터의 serviceName/RequestContext 초기화.

성능 목표는 절대 시간으로 고정하지 않는다. 소비자 앱에서 DevTools와 동일 변경을 비교하여 컴파일 완료부터
첫 성공 응답까지의 시간, 부모 자원 재생성 횟수, 반복 교체 후 메모리를 측정한다. 지연 초기화나 첫 요청으로
작업을 미룬 효과를 재로딩 개선으로 집계하지 않는다.
